# 界面层技术选型

| 项       | 决策                                      |
| -------- | ----------------------------------------- |
| 归属     | mindx-work · UI 框架（shell）             |
| 状态     | 定稿（2026-09-24）                        |
| 渲染库   | Vue 3（Composition API + SFC）            |
| 状态管理 | Pinia                                     |
| 桌面宿主 | Electron                                  |
| 样式实现 | CSS Modules + `--mx-*` token              |
| 工程底座 | pnpm workspace + Vite + TypeScript strict |

> 上游契约见[组件层契约](./组件层契约.md)——契约保持渲染库无关，本选型只决定**先实现哪个适配器**，契约文档不因此改动。

---

## 1. 渲染库：Vue 3 + Pinia

**选择理由**：

- 响应式模型与 SwiftUI `@Observable` 心智同构，声明式直改即更新，无 hooks 闭包/手动 memo 负担。
- Pinia store 是 `services.provide` 的理想实现——provide 进去的就是响应式本体，消费端零桥接；状态管理问题随选型一并解决。
- 模板编译期优化，同场景产物更小。

**后果**：

- 第一个适配器为 `ui-shell-vue`：条目 `component` 收窄为 Vue 组件类型；`ui-shell-react` 延后，架构不依赖。
- 内核（shell-core）仍渲染无关：机制状态（activeId、shown、overlay 栈）为可变结构 + 版本订阅，由适配器映射为 Vue 响应式。
- 插件内部状态一律 Pinia；`services` 通道中流动的是 store 实例。

## 2. 桌面宿主：Electron

**选择理由**：与现有 mindx desktop 同栈，工程惯性共享；Chromium 渲染一致性最好。

**项目语言边界**：mindx-work 全栈 NodeJS——主进程、渲染进程、预置插件均为 Node/TS 生态。

**后果（硬纪律）**：

- **主进程只做窗口壳**：窗口生命周期、原生菜单、Dock/托盘等系统能力，禁止业务逻辑，也不做消息转发。
- **Agent 服务是服务插件**：Agent 服务在本项目建成之后，以服务插件形式经 `services.provide` 挂载进壳，成为普通服务；其连接与协议细节归该插件自理，Electron main 对其零感知。
- **安全基线**：`contextIsolation` 开启，渲染进程无 `nodeIntegration`；preload 仅暴露窗口级能力。

## 3. 工程形态

```text
mindx-work/
├── ui-shell/          # 内核：AppShell + 六区 + 插件契约（渲染无关，零 Vue 依赖）
├── ui-shell-vue/      # Vue 适配器：条目渲染 + 类型收窄（C = Vue 组件）
├── plugins/           # 预置插件（Pinia；daemon-link 通信插件在此）
├── electron/          # 主进程窗口壳（薄，无业务）
└── app/               # 组装入口：createApp(预置清单) + Vue 挂载
```
