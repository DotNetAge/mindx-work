# mindx-work 壳机制审计

## 何时使用

- 用户要求对 mindx-work 做全面代码审计、安全审查、机制健康检查时。
- 大规模迭代收尾前的主动体检；或发现一类缺陷后排查同类问题（定向审计——按 references/checklists.md 对应分片裁剪，不必四片全跑）。
- 分流出口：普通功能开发走 mx-dev-guide 分流；本技能只做"审计 → 分级 → 修复 → 回归"闭环，不做新功能设计。

## 审计总则（军规）

1. **审计 = 对照，不是浏览**：每条检查都是"代码 vs 契约/军规"的差异比对。基线 = mx-plugin-dev `references/contract.md`（六区契约 + §12 校验 + §17 数据校验边界 + §18 动态插件）+ mx-uikit 样式军规 + mx-dev-guide 基本军规。给不出契约依据的"看不顺眼"不是发现。
2. **证据军规**：每条发现必须给出 `文件路径:行号` + 触发条件 + 后果链（谁在什么时机会遇到什么）。给不出行号的发现不许进报告。
3. **trust but verify**：子代理返回的高危结论，主会话必须亲读代码复现确认后才能进最终报告——子代理摘要只是线索，不是证据。
4. **只报正确性 / 安全 / 健壮性**：禁止风格化建议（命名、格式偏好）、禁止过度工程建议（"可以加个抽象"）。观察档只记录不一致，不强制修。
5. **禁止猜测**：并发时序、竞态、安全边界类结论必须能沿代码路径走通（谁先谁后、哪一步可被打断、打断后留下什么状态），走不通的路径不写。

## 分片并行法

按包切四片，子代理（general-purpose）并行审计，每片一份任务书（清单见 references/checklists.md）：

| 片 | 范围 | 审计焦点 |
| --- | --- | --- |
| 一 | ui-shell 内核（渲染无关层） | 并发一致性、校验顺序、状态机、契约符合性 |
| 二 | ui-shell-vue 渲染层 | 事件监听生命周期、指针交互、样式军规 |
| 三 | plugins + app 编排层 | 异步时序、防重入、清理隔离、激活期校验 |
| 四 | electron 宿主安全 | SSRF 边界、路径安全、资源上限、持久化健壮性、IPC 面 |

任务书模板：**审计范围**（文件清单）→ **对照条款**（契约节号）→ **检查项** → **该片已知坑**（实证教训，供对照是否复发）→ **输出格式**（分档 + 文件：行号 + 后果链）。四片报告合并去重 → 主会话亲证高危 → 排 P0/P1/P2 修复序。

## 发现分级

| 档 | 定义 | 处置 |
| --- | --- | --- |
| 缺陷 | 现有代码路径可实证触发的错误行为（并发错序、状态污染、监听泄漏、校验绕过） | 必修，按 P0/P1 排序 |
| 风险 | 防线缺失或特定条件下可触发（安全边界、资源上限、错误消息透传英文） | 应修；安全类一律升 P0 |
| 观察 | 不一致、残留、可读性 | 记录，不强制修 |

## 修复闭环

1. 修复按 P0 → P1 → P2 推进；**同一文件多处修改逐条串行编辑并逐一回读验证**——对同一文件的并行 Edit 会写回竞争（后写覆盖先写，部分编辑静默回滚），主会话与子代理均实踩。
2. 每处修复的注释必须与行为一致（注释撒谎比没注释严重）；错误消息一律中文。
3. 修复完成 = `pnpm typecheck` + `pnpm lint` 全绿 + 涉及机制的改动走真机验收（读 mx-dev-guide `references/architecture.md` §7 四步循环，verify 脚本断言全绿）。
4. 修复产生的新实证坑必须回写：契约条款变化 → mx-plugin-dev `references/contract.md`；机制变化 → 本技能 `references/checklists.md` 对应分片的"已知坑"。
