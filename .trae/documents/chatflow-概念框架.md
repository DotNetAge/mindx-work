# ChatFlow 概念框架（讨论稿）

> 状态：讨论进行中——本文沉淀已达成的设计意图与开放问题，作为后续讨论与实施的基线。
> 来源：两轮讨论。①壳级插件体系下的「插件中的插件」槽位机制；②ChatFlow 概念框架（任务导向、Session 数据模型、轮组织、双视图、输出管理、两大接口组件）。
> 配套：mindx-desktop 实证代码 `src/renderer/src/components/chat/`（下称"Desktop 实证"）；壳契约 `mindx-work/.agents/skills/mx-plugin-dev/references/contract.md`。

---

## 1. 定位

ChatFlow 是 mindx-work 中**变化量最大的插件**：承载 mindx-desktop chat 体系（对话树、工具呈现、输入区、会话列表）的移植，并确立"任务导向"的产品心智。复杂度管理靠正式化契约 + 变化局部化，而非结构堆叠。

---

## 2. 契约系统（复杂度管理的骨架）

ChatFlow 的全部交互过程由三层契约界定结构边界：

| 契约层 | 内容 | 管理手段 |
| --- | --- | --- |
| 壳契约（既有） | 六区席位、services 通道、启动期校验 | contract.md，零改动 |
| 数据契约 | Session → 消息流 → TreeNode 判别联合；四张注册表（components / summary / actions / icons）按 `TreeNodeType` 穷举键控 | 漏类型编译报错（编译期穷尽，Desktop 实证 §4.2） |
| 槽位契约（扩展） | `ChatFlowSlotHost` / `ChatFlowSlotSpec`：presentation 必填 + view / actions 可选 | 保留键 + 冲突抛错 + 五层防线 |

原则：**类型即契约**（同进程信 TS，校验只做静态覆盖不了的——跨扩展冲突、保留键、id 形状）；**变化局部化**——ChatFlow 的高频变化被贡献层吸收，壳零感知。

---

## 3. 数据模型：以 Session 为根的层级结构

- **Session = 会话数据的根容器**：元信息、消息流、模型/配置、任务态的唯一入口。
- 消息流经 builder 归一为节点树（TreeNode 判别联合：执行内容 / 实体协作 / 阻塞系统 / 工具四族）。
- Desktop 实证：`tree/builder/`（groupBuffer 分组、restore 历史恢复、tool-map 消息归一）+ `tree/types/`（base / content / entity / system / tool / visitor）。
- **归属边界**：Session 模型、builder、会话 store 归 ChatFlow 本体；扩展零触碰，只经 props 消费节点数据。

---

## 4. ChatRound：长对话的组织原则

ChatRound **不是具体数据实体，而是组织抽象**（视图/交互层面的轮容器）。尽管非具体数据，仍必须作为一等组织原则固化：

### 4.1 一轮的五要素

1. 用户查询/输入
2. 执行序列（工具调用日志）
3. 推理/思考序列
4. 最终输出内容
5. **轮分界标记**（清晰可辨的边界）

### 4.2 数据级与视图级的分工

- **数据级分界**：用户消息节点即轮头——分界标记的物理载体。builder 与 restore 必须保证历史恢复后轮分界完整。
- **视图级聚合**：轮容器把五要素聚合成可扫读单元。Desktop 有两代实证（ChatRound 复合组件 + tree 树壳），ChatFlow 取其**组织原则**、以树壳承载。
- **轮是用户交互的主操作单元**：回退/删除/复制以轮为界（Desktop 实证：UserMessageRow 行内操作）；任务连贯性由轮保证——一轮即一个任务片段，长对话 = 轮序列。
- **轮形态定稿（2026-09-26）**：流水线 + 分隔线——内容按序排布，轮间用细分隔线，不引入轮容器框（对齐「简单、无边框节点」既定偏好）。

### 4.3 轮内从属组件

| 组件 | 职责 | Desktop 实证 |
| --- | --- | --- |
| 用户消息对象 | 轮头呈现 + 回退/删除/复制 | UserMessageRow |
| 推理/工具调用过程 | 思考区 + 推理区 + 执行区（工具→文案映射、流光态） | ProcessView（ThinkingView / ActionsView / BashTerminalView / TaskListView） |
| 结果生成机制 | 最终答案 markdown + token 用量 + context 进度 | ResultView |
| 长尾消息 | 错误 / 压缩 / 最大轮次 / 重试警示，仅命中时显示 | ErrorView / CompactionView / MaxTurnsWarning / LLMRetryWarning |

### 4.4 历史加载与压缩：渐进式加载 + 游标折叠（2026-09-26 定稿）

ChatFlow 对压缩的处理**与 Desktop 分道**：Desktop 压缩即清理，ChatFlow 折叠不清链。双场景：

| 场景 | 策略 |
| --- | --- |
| 进入已有会话 | **渐进式加载**：首屏只加载最近 3 轮；向上滚动翻查历史，按 3 轮一页向上续载 |
| 实时对话 | 持续插入；界面超过 10 轮后，10 轮前的轮次在后台移除 DOM（用户无感，界面不爆炸） |

压缩语义（Daemon 配合）：

- Daemon 保留会话**全部消息**（日志可查）；发给 LLM 的只是活跃上下文窗口内的轮次，窗口边界用**游标**标识
- 客户端持久化历史消息 + 游标：前端遇到游标，渲染 `----历史消息已压缩----` 占位分隔符，并把其前的消息**折叠**（不清理、不断链）
- 收益：压缩发生后历史完整可回溯，轮分界永不丢失；滚动加载与压缩占位天然兼容

## 5. 工具复杂度：核心架构与双视图

### 5.1 执行与呈现分离

- **工具执行归 MindX 核心**：内置工具 + 第三方扩展工具统一走核心工具架构；ChatFlow 不执行工具，只呈现其痕迹。
- 两个扩展点对称但独立：核心侧扩展 = 新工具落地；呈现侧扩展 = ChatFlow 槽位注册新节点类型的渲染。

### 5.2 双视图渲染

| 视图 | 受众 | 形态 | Desktop 实证 |
| --- | --- | --- | --- |
| 过程侧（Agent 视角） | 需要审计过程的场景 | 展开态 / 全卡直渲（standalone），承载终端、diff、命中列表等完整过程 | 树壳展开容器 + standalone 视图 |
| 用户侧（简化视角） | 日常扫读 | 统一名片 = 图标 + 状态动词 + 对象 + 元信息徽标（四要素） | summary.ts §3.3、NodeCard |

### 5.3 内容过滤

**结构化供给 ≠ 全量显示**：object / badges 只做精选投影，禁止 payload 原样 dump（Desktop 实证：summary.ts 取舍 18）。流式期间的呈现同样收口（executing 流光文案 + 树尾 pending 行，措辞同源）。

## 6. 输出管理系统

四类输出统一收口：

| 输出类型 | 承载 | 确认语义 | Desktop 实证 |
| --- | --- | --- | --- |
| 文本回答 | content 节点（markdown + 操作组：复制/朗读/下载/保存） | 无 | ContentView、actions.ts 答案形态操作组 |
| 生成文件 | write / edit 节点 + 文件行、diff 回看 | 无（已落盘） | WriteNodeView / EditNodeView / DiffBody |
| **待确认修改集** | permission / ask_user 阻塞节点 + 底部交互区 | **必须用户确认才落地** | PermissionBar / AskUserView / PermissionNodeView |
| 其他媒体 | 按节点类型注册视图（图片/文档徽标已有实证） | 按类型 | tool.read 的 format 徽标 |

### 6.1 产物视图（Detail 轨道，2026-09-26 定稿）

会话产物的聚合呈现面，挂壳 Detail 轨道（默认 320、可拖拽，几何归壳，contract §14）。

- **席位归属**：ChatFlow **本体**注册的 Detail 条目（单 tab，标题定稿「产物」）；扩展无权（见 §8）。
- **触发语义**：会话内出现文件新增/修改（write / edit 工具痕迹）时**自动拉出**（Detail.show）；**用户手动关闭后，本次会话内不再自动拉出**，手动点开不受影响。
- **三段结构**（自上而下，对照参考截图）：

| 段 | 内容 | 备注 |
| --- | --- | --- |
| 对话产物 | 会话产生的正式产物 | 行右侧 + 按钮**第一版不实现**（位置预留） |
| 技能 | **本会话用到的**技能 | 空态「暂无内容」 |
| 最近文件 | 最近被修改/新增的文件行（类型图标：文档 / 图片缩略图等） | 实时累计 |

- **空态**：各段「暂无内容」（对齐参考截图形态）。
- **数据源**：文件变更来自会话内 write / edit 工具痕迹；技能段为本会话的技能激活记录。
- 与开放问题的关系：**文件类产物的聚合呈现由此视图承接**；轮内粒度聚合仍留开放（见 §9）。

### 6.2 前置依赖与演进（Daemon 侧，2026-09-26）

**§6.1 产物视图的前置条件**——以下两项完成前，产物视图不成立（其技能段、产物溯源均依赖工作目录级存储）：

2. **项目化技能落位**（TODO #L13 + 《目录局部技能进化系统》设计文档 v0.1）：项目化 skill 进入 `.agents/skills`；设计文档给出双链路——**链路 A 自动沉淀**（前置轻量过滤 → 压缩+识别合并为单次 LLM 调用 → 只新增不修改）、**链路 B skill-merger 人工复盘合并**（预览清单 → 用户确认 → 归档备份）。

**目录定稿（2026-09-26）**：`.sessions` 与 `.agents/skills`——均为**社区事实标准**；设计文档 §3.1 的 `.session/`、`.agents/.skills/` 写法作废。

**遗留口径**（设计文档推测部分，实施时以代码校准、不照单全收）：

2. **归档备份落位**：`.agents/skills` 为扁平标准目录，设计文档 `archive/{timestamp}/` 的备份机制需另定位置——链路 B 硬性规则「永不删除原始文件」依赖它。

**演进预留**：产物视图后续增加**「进化」按钮**——人工触发 skill-merger 复盘合并（设计文档链路 B 的界面入口），不做自动后台执行。

**时序（2026-09-26）**：先完成 ChatFlow 移植，再进 Daemon 大修；**移植期间不动 Daemon**，上述前置依赖仅作挂起记录。

## 7. 两大接口组件（同优先级）

1. **ChatInput 增强模块**（2026-09-26 定稿）：
   - Desktop 输入区功能**全量移植**（fileRefNode 文件引用、NoModel 未配模型占位等）
   - 第一波增强**四项全做**：@ 引用、附件上传、模型快速切换、任务上下文自动携带
   - **空会话 hero 形态**：新对话未开始时，ChatInput 居中呈现在 Content 中部；上方为带 Logo 的标题「探索人机共生的新时代」，并带 beta 上标（对齐 DeepSeek Harness 式"主区居中 hero + 大输入卡"）
2. **侧栏会话列表，命名定稿为「Tasks」**（**不叫「会话 / Conversations」**）：强调任务导向心智——每个会话是一个任务，不是一段聊天记录。
   - 席位归属：由 ChatFlow **本体**注册 Sidebar 分节（ChatFlow 是壳插件，有权占壳席位）；**扩展无权**（见 §8）。
   - 行信息定稿（2026-09-26）：任务名 + 运行状态 + 最后活动时间 + 未读标记；**不做内容预览**。
   - **新增 Session.title 属性**（跨层特性）：Daemon 同步支持——新建 Session 时由大模型从用户问题提炼任务名称（突出用户意图）；用户可编辑 title，补齐 Desktop 缺失的能力。
   - **列表形态二次定稿（2026-09-26，全量分组制）**：Desktop 只显示当前工作目录下的任务；Work 版强调快——**一次性拉取当前 Agent 的全部会话**，在本地按**目录名（工作目录去路径）**分组呈现。
   - **点击语义（捷径）**：点击任务行 = 直接打开该工作目录 → 加载该 Session 内的消息。加载链 **Model → Agent → Session** 中，Agent 与全量分组已就位，点击只剩目录切换 + 消息加载，一步直达。
   - **「最近讨论」捷径区（Finder 式）**：Tasks 分组列表之下增设**不分组**的「最近讨论」——取**整个 Daemon 范围**内时间上最近活跃的会话（跨 Agent）。选中流程 = **先切 Agent → 再切会话**；若 Agent 发生变化，上方的 Tasks 分组列表随之刷新。
   - **Daemon 配合项**：①按 Agent 全量会话列表查询；②Daemon 级最近活跃会话查询（跨 Agent）；③Session.title 属性（前述）。

## 8. 槽位机制（插件中的插件）——讨论沉淀摘要

详细机制见讨论记录与项目记忆，此处只留结论：

- **扩展不是壳插件**：只持 `ChatFlowSlotHost`，签名无 AppShell（能力不传递）；Content 席位归 ChatFlow 唯一持有，扩展物理上无法触壳任何席位。
- **槽位三件套**：presentation（必填，统一名片四要素）/ view（可选，standalone 语义同内建）/ actions（可选，id 仅限既有 `NodeActionId` 枚举——分派器在 useNodeActions，属 ChatFlow 内部）。
- **内建四表穷举保留**：贡献层只服务后端新增的节点类型，内建键（含 null 键）不可认领；查找链 = 贡献层优先、内建层兜底。
- **五层防线**：类型层（签名无壳）/ 装载层（不入壳插件循环）/ 校验层（启动期违规抛错 = 装配失败）/ CI 静态层（禁越界 import）/ 渲染层（唯一出口 = 树壳 `<component :is>` 分派）。
- **通道分治**：跨插件数据走壳 services；UI 呈现扩展走槽位——两通道互不相干。
- **v1 不做**：market 动态插件开放槽位（无 import 通道，嫁接必残废）、内建键覆盖、输入区/轮级/底部 Drawer 槽位、扩展间共享。
- **共享件纪律**：扩展禁 import ChatFlow 内部组件（DiffBody 等）；确需复用按"共享型组件上提"提为中立 ui 包。
